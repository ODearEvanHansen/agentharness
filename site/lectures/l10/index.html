    第 10 讲 · 子 agent 与编排¶

    spawn 与 fork、深度限制、结果回传

    视频制作中

    本讲视频将发布在 B 站，届时在这里嵌入播放。下面是讲稿正文。

    第十讲，我们讲子 agent 与编排。一个 agent 能不能把任务拆开，交给别的 agent 去做？什么时候值得这么做？本视频由程序合成，配音来自 DeepSeek 语音合成。

    DSH 怎么定义子 agent¶

    The subagent package family lets an agent delegate a task to a child, continue the child's work, and discover every child it created.

    —— packages/subagent/README.md @ dsh-v0.2.2-rc.2

    先看 DSH 文档的定义：子 agent 模块让一个 agent 把任务委派给子级，继续子级的工作，并且能发现它创建过的所有子级。委派、继续、发现，这就是子 agent 的三个基本动作。

    要点

    委派、继续、发现：子 agent 的三个动作

    spawn 还是 fork¶

    spawn：全新的子 agent

    • 从空白上下文开始
    • 只拿到任务描述
    • 适合独立、边界清楚的子任务

    fork：带历史的子 agent

    • 以父级已完成的历史为起点
    • 知道前面聊过什么
    • 适合需要前文背景的任务

    DSH 提供两种进程内的子 agent。spawn 从空白的上下文开始，只拿到任务描述，适合边界清楚、彼此独立的子任务。fork 以父级已经完成的对话历史为起点，适合需要前文背景的任务。此外，还可以通过 ACP 等协议，把别的 agent 程序当作进程外的子 agent。

    要点

    还可以把 ACP、Codex、Claude Code 当作进程外子 agent

    深度和并发：防止失控¶

    见 docs/subsystems/subagent.zh.md

    • 子 agent 还能再派子 agent：maxDepth 给委派深度设上限
    • 后端要声明 depthLimit 能力，否则带 maxDepth 的请求会被拒绝
    • 多个子 agent 可以并行跑：M0 原型里派 2 个并行子 agent，树上挂 2 个子节点
    • 每个子级对父级可见，无论运行中还是已存储

    子 agent 自己还能再派子 agent，所以必须限制深度。DSH 用 max depth 设定委派深度的上限，后端如果不支持这个能力，请求会直接被拒绝。子 agent 也可以并行，M0 的原型里同时派了两个子 agent，agent 树上就挂出两个子节点。而且每个子级对父级始终可见。

    要点

    不设深度上限，递归委派会把预算吃光

    结果怎么回传¶

    delivery 字段决定结果送到哪里

    • parent：结果作为消息通知父级模型，面向模型的工具都用这种方式
    • caller：只把结果返回给调用方，不往父级注入消息
    • 观察时用 subagent.started 和 finished 事件建立父子关系
    • 成本要把子 agent 的会话一起汇总，否则会低估

    结果怎么回传？DSH 有两种方式。parent 方式把结果作为消息通知父级模型；caller 方式只把结果交给调用方，不往父级的对话里塞消息。在作业一里观察时，要靠 subagent started 事件建立父子关系，算成本时也要把子 agent 的会话一并汇总，否则会低估花费。

    要点

    子 agent 的成本藏在另一个会话日志里

    一个真实例子：把子任务交给本地模型¶

    作业五 M0 实测：主 agent 用 deepseek-flash，子 agent 用本机 Qwen3-Coder-30B-A3B

    项目 数值
    主 agent 请求数 7
    子 agent 请求数 6

    来看作业五的一个实测例子。主 agent 用 deepseek flash，把统计文件的子任务交给本机的一个开源模型。主 agent 发了七次请求，花了零点零零四六美元；子 agent 发了六次请求，本地运行，不花 API 费用。答案是对的。但有个问题：主 agent 拿到结果后，自己又算了一遍来复核。

    要点

    主 agent $0.0046，子 agent 本地 $0；答案正确

    子 agent 什么时候值得用¶

    • 值得：子任务独立、输出可以压缩成短结论，例如搜索代码、总结日志
    • 值得：想把脏活交给便宜的模型，同时不污染主 agent 的上下文
    • 不值得：父级不信任结果、要自己复核，省下的钱又花回去
    • 不值得：任务紧密耦合，来回传递上下文比自己做还贵

    那么子 agent 什么时候值得用？当子任务独立，结果可以压缩成一句短结论时，比如搜代码、总结日志，子 agent 能让主 agent 的上下文保持干净，还能交给更便宜的模型。反过来，如果父级不信任结果，要自己复核，或者任务耦合太紧，来回传上下文的代价就会超过收益。

    要点

    衡量标准：总成本和解决率，而不是看起来更高级

    小结¶

    • spawn 空白开始，fork 带着历史
    • maxDepth 限制委派深度
    • delivery：parent 或 caller
    • 成本要连子会话一起算
    • 不信任结果，就省不了钱

    小结一下：spawn 从空白开始，fork 带着历史；用最大深度防止失控；结果可以回给父级或调用方；成本要连子会话一起算。课后练习：用作业一的工具派两个并行子 agent，检查树和总成本。下一讲，上下文工程。
