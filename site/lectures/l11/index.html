    第 11 讲 · 上下文工程¶

    系统提示、压缩、工具结果裁剪：token 都花在了哪里

    视频制作中

    本讲视频将发布在 B 站，届时在这里嵌入播放。下面是讲稿正文。

    第十一讲，上下文工程。agent 每一步都要把整段上下文重新发给模型，所以上下文里放什么、放多少，直接决定成本和效果。本视频由程序合成，配音来自 DeepSeek 语音合成。

    一次请求里有什么¶

    每一步都要重新发送全部内容

    固定部分     系统提示 | 工具定义
历史       用户任务 | 模型消息 | 工具结果（常常最大）
新增       这一步的新内容

    先看一次请求里有什么。开头是系统提示和工具定义，接着是全部历史，包括用户任务、模型的回复和工具结果，最后是这一步新增的内容。DSH 的文档说得很直接：系统文本和工具定义，每一步都要再付一次钱。

    要点

    系统提示和工具定义每一步都要再付一次钱

    token 都花在了哪里¶

    M0 实测，SWE-bench 20 题，每题平均

    项目 数值
    自写 loop 输入 703k
    DSH 输入 415k
    自写 loop 输出 12.7k
    DSH 输出 8.6k

    token 都花在了哪里？M0 在二十道 SWE bench 题上实测，自写 loop 每题平均输入七十万 token，DSH 是四十一万；而输出只有一万出头。输入是输出的几十倍，所以上下文工程的重点，就是控制输入。

    要点

    输入远大于输出：优化重点在输入

    第一招：系统提示与工具描述¶

    写得好，可以直接减少步数

    • 完整 sdk 配置的系统提示加工具定义约 1 万 token
    • sdk-minimal 只有一个 bash 工具，系统提示一句话
    • DSH 的 bash 描述引导模型一次写文件并运行：小题上请求数 2.3 对 4.9
    • 提示里别放会变的东西，比如当前时间（第十二讲）

    第一招是系统提示和工具描述。完整的 sdk 配置，系统提示加工具定义大约一万 token；sdk minimal 只有一个 bash 工具。描述写得好，能直接减少步数：在小题上，DSH 的 bash 描述引导模型一次写完文件并运行，平均二点三次请求，自写 loop 要四点九次。

    要点

    步数少了，每一步重复发送的上下文也就少了

    第二招：工具结果裁剪¶

    assignment3/templates/trim-tool-output.ts（节选）

    ctx.on('tools/post-execute', async (exec, result, next) => {
  if (result?.isError || !Array.isArray(result?.content)) return next()
  ...
  const head = Math.floor(maxChars * headRatio)
  const tail = maxChars - head
  const omitted = block.text.length - head - tail
  // text = head chars + one-line omission note + tail chars
})

    第二招是裁剪工具结果。作业三的插件模板挂在工具执行之后，结果进入上下文之前。如果输出太长，就只保留开头和结尾，中间换成一行提示，告诉模型可以用更精确的命令去查。

    要点

    保留开头和结尾，中间换成一行省略提示

    裁剪的效果：小实验 vs 真实任务¶

    作业三 M0 实测

    项目 数值
    小实验 不裁剪 $0.00259
    小实验 裁剪 $0.00088
    SWE 20 题 基线 $0.018/题
    SWE 20 题 裁剪 $0.0170/题

    效果如何？在一个专门设计的小实验里，运行一个输出三千行的脚本，裁剪后成本从零点零零二五九美元降到零点零零零八八美元，约三分之一，答案仍然正确。但放到二十道 SWE bench 题上，解决数都是十七道，每题成本从零点零一八降到零点零一七美元，几乎没有变化。

    要点

    小实验成本降到约 1/3；SWE-bench 上几乎没有变化

    为什么收益没有迁移¶

    作业三 README 给的提示

    • DSH 的 bash 工具本来就会截断输出
    • 模型很少把长输出原样打印出来
    • 小实验的收益，不一定能迁移到真实任务
    • 先测量 token 花在哪里，再决定优化什么

    为什么没有迁移？一方面，DSH 的 bash 工具本来就会截断输出；另一方面，模型很少把很长的输出原样打印出来。这说明，小实验里的收益不一定能迁移到真实任务。正确的顺序是先测量 token 花在了哪里，再决定优化什么。

    要点

    先测量，再优化

    第三招：压缩¶

    DSH 的 compaction 是一项可选能力

    • 不属于 agent loop 主干，由独立插件提供
    • 把一段历史替换成一条摘要消息，记录被遮蔽的范围和 token 数
    • 代价：被替换处之后的前缀缓存失效，摘要还可能丢细节
    • 什么时候压缩、压缩什么，是作业三可以调的策略

    第三招是压缩。在 DSH 里，压缩是一项可选能力，不在 agent loop 的主干里。它把一段历史替换成一条摘要消息。这能省下很多 token，但也有代价：被替换的位置之后，前缀缓存就失效了，摘要还可能丢掉关键细节。什么时候压缩，压缩什么，是作业三可以调的策略。

    要点

    压缩省 token，但会打断前缀缓存

    小结¶

    • 输入远大于输出，优化重点在输入
    • 工具描述影响步数
    • 裁剪工具结果：小实验有效，真实任务未必
    • 压缩省 token，但会打断缓存

    小结：输入是成本大头；工具描述能减少步数；裁剪在小实验上有效，在真实任务上未必；压缩能省 token，但会打断缓存。课后练习，完成作业三的第二关。下一讲，我们专门讲前缀缓存。
