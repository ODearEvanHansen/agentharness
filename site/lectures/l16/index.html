    第 16 讲 · 案例复盘：作业三的优化方案¶

    小实验的收益，为什么没能迁移到 SWE-bench

    视频制作中

    本讲视频将发布在 B 站，届时在这里嵌入播放。下面是讲稿正文。

    第十六讲是一次案例复盘。作业三今天截止，我们用课程团队自己跑过的一个方案，完整走一遍从想法、小实验、真实评测到结论的过程。本视频由程序合成，配音来自 DeepSeek 语音合成。

    复盘对象：工具输出裁剪插件¶

    assignment3/templates/trim-tool-output.ts

    • 想法：工具输出太长，会在之后每一步被重复发送，浪费 token
    • 做法：挂在 tools/post-execute 上，超过阈值只保留开头和结尾
    • 中间替换成一行省略提示，引导模型用 grep 或 sed -n 精确查看
    • 不改 DSH 源码，只通过 patch 文件插入插件

    我们复盘的方案，是作业三提供的模板插件：工具输出裁剪。想法很直接，工具输出太长，会在之后的每一步被重复发送给模型。所以插件挂在 tools post execute 上，输出超过阈值时只保留开头和结尾，中间换成一行省略提示，提醒模型用更精确的命令去查看。整个过程不改 DSH 源码。

    要点

    一个直觉上很合理的优化

    核心代码¶

    assignment3/templates/trim-tool-output.ts（节选）

    ctx.on('tools/post-execute', async (exec, result, next) => {
  ...
  const head = Math.floor(maxChars * headRatio)
  const tail = maxChars - head
  const omitted = block.text.length - head - tail
  return { ...block,
    text: block.text.slice(0, head) + NOTE(omitted) + block.text.slice(-tail) }
  ...
  return changed ? { kind: 'accept', content } : next()
})

    核心代码只有十几行，这里为了显示做了简化。按 head ratio 算出开头保留多少，剩下的留给结尾，中间记下省略了多少字符。注意最后一行：如果内容被改了，就返回 accept，否则调用 next，交给下一个插件处理。这就是 waterfall 挂载点的写法。

    要点

    waterfall 挂载点：改了就 accept，没改就交给下一个

    小实验：成本降到约三分之一¶

    M0 实测，sdk-minimal，输出 3000 行的脚本再回答三个问题

    项目 数值
    不裁剪 · 成本 $0.00259
    裁剪 2000 字符 · 成本 $0.00088

    先看小实验。任务是运行一个输出三千行的脚本，再回答其中三行是什么。不裁剪时，成本约零点零零二六美元；裁剪到两千字符后，降到零点零零零九美元左右，大约三分之一，答案依然正确。模型看到省略提示后，自己换了一条更精确的命令。

    要点

    未命中输入 token：6,441 → 1,063，答案都正确

    要点

    真实运行记录（前 8 题）

    结果：几乎没有变化¶

    基线 sdk-minimal

    • 解决 17 / 20
    • 每题 $0.018
    • 缓存命中率 95.8%

    开启裁剪插件

    • 解决 17 / 20
    • 每题 $0.0170
    • 缓存命中率 96.1%

    结果是，解决了十七道，每题零点零一七美元，缓存命中率百分之九十六点一。基线也是十七道，每题零点零一八美元。差别几乎为零，完全在运行之间的随机波动范围内。

    要点

    小实验的收益，不一定能迁移到真实任务

    为什么没效果？¶

    复盘要回答的核心问题

    • DSH 的 bash 工具本来就会截断输出，插件很少被触发
    • 模型很少把长输出原样打印出来，会主动用 head、grep
    • 成本大头在多步累积的上下文，而不是单次长输出
    • 教训：先测量真实任务里问题出现的频率，再决定优化什么

    为什么没效果？第一，DSH 的 bash 工具本来就会截断输出，插件很少有机会触发。第二，模型在真实任务里很少把长输出原样打印出来。所以小实验里放大的问题，在真实任务里并不常见。教训是：先测量问题在真实任务中出现的频率，再决定优化什么。

    要点

    先测频率，再做优化

    一份好的作业三报告长什么样¶

    • 每个结论都有对照，只改一个变量
    • 说明如何处理随机性：重复几次，报告方差
    • 成本按高峰价统一计算，单独报告缓存命中率
    • 负结果也是结果：讲清楚为什么无效

    最后总结一份好报告的标准。每个结论都要有对照，而且只改一个变量。说明你怎么处理随机性。成本按高峰价统一计算，并单独报告缓存命中率。还有，负结果也是结果，只要你讲清楚它为什么无效。

    要点

    负结果，写清楚原因，同样有价值

    小结¶

    • 裁剪插件在小实验中把成本降到约 1/3
    • SWE-bench 20 题：17/20，$0.0170 vs 基线 $0.018
    • 原因：bash 工具自带截断，长输出很少出现
    • 先测量问题频率，再优化

    小结一下。裁剪插件在小实验里很有效，在真实任务上却几乎没有作用。原因是问题本身很少出现。下一讲，我们进入推理服务，从预填充和解码讲起。

    课后练习

    统计你自己一轮 SWE-bench 运行中，工具输出超过 4000 字符的次数占比，判断裁剪插件值不值得开
