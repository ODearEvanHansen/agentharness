    第 21 讲 · 显存与内存管理¶

    PagedAttention 与 KV 量化

    视频制作中

    本讲视频将发布在 B 站，届时在这里嵌入播放。下面是讲稿正文。

    第二十一讲，显存与内存管理。K V cache 用内存换计算，那么内存本身怎么管？今天讲 PagedAttention，以及 K V 量化为什么在 CPU 上反而变慢。

    问题：按最大长度预留，浪费严重¶

    传统做法给每个请求预留一整块连续空间

    请求 A     已用 | 预留但没用
请求 B     已用 | 预留但没用
请求 C     内存不够，进不来

    先看问题。推理服务不知道一个请求最终会生成多长，传统做法只好按最大长度，给每个请求预留一整块连续空间。结果大部分空间预留了却没用，新请求反而因为内存不够进不来，并发数上不去。

    要点

    不知道会生成多长，只好按最长的预留

    PagedAttention：像操作系统一样分页¶

    vLLM 论文的思路（只讲不做）

    请求 A     页1 | 页2
请求 B     页1 | 页2 | 页3
请求 C     页1
空闲页      空闲 | 空闲 | 空闲

    vLLM 论文借鉴了操作系统的虚拟内存。K V cache 被切成固定大小的块，按需分配，不要求物理上连续，用一张块表记录映射。这样几乎没有浪费，相同前缀的块还可以在请求之间共享。

    要点

    按需分配固定大小的块，不再要求连续

    另一条路：把 KV cache 量化¶

    f16 → q8_0，每个元素占用减半

    • llama-server：--cache-type-k / --cache-type-v q8_0
    • 需要同时开启 Flash Attention：-fa on
    • 直觉：KV 变小，内存更省，读得更快
    • 作业四 E4 就是检验这个直觉

    另一条路是把 K V cache 本身量化，从十六位浮点换成八位。在 llama server 里用 cache type 参数设置，并且要同时打开 Flash Attention。直觉上，K V 变小了，应该更省内存、更快。作业四的实验四就是来检验这个直觉的。

    要点

    直觉对不对，要用数据说话

    E4 实测：f16 对比 q8_0¶

    a4_E4：Qwen3-8B Q4，32k 上下文，Xeon Gold 6354，-t 16

    $ python assignment4/engine/bench.py --exp E4 --model models/Qwen3-8B-Q4_K_M.gguf --server llama.cpp/build/bin/llama-server
  "kv_f16": {
   "rss_mb": 12757,
   "pp_tok_s": 89.2,
   "tg_tok_s": 10.21
  },
  "kv_q8_0": {
   "rss_mb": 10599,
   "pp_tok_s": 36.4,
   "tg_tok_s": 9.23

    看真实结果。量化后常驻内存从一万两千七百多兆降到一万零六百兆左右，省了一些。但预填充速度从每秒八十九个 token 降到三十六个，生成速度也从十点二降到九点二。在 CPU 上，K V 量化反而变慢了。

    要点

    内存略省，但预填充和生成都变慢了

    试做阶段：30B-A3B 也是同样趋势¶

    M0 报告 E4，30B-A3B，32k 上下文，-t 16，生成 tok/s

    项目 数值
    KV f16 25.2
    KV q8_0 19.3

    试做阶段用三十 B A 三 B 模型测试，趋势一样：生成速度从二十五点二降到十九点三，常驻内存基本没变，因为十八点六 G 字节的权重才是大头。

    要点

    RSS 基本相同：权重占了大头

    为什么在 CPU 上反而变慢¶

    必答问题的思考方向

    • 每次注意力计算前，都要额外做反量化
    • CPU 上这部分开销没有被专门优化的内核抵消
    • 短上下文、单并发时，KV 本来就不是内存大头
    • GPU、长上下文、高并发时，结论可能反过来

    为什么会这样？量化后的 K V 在每次注意力计算前都要反量化，这是额外的计算。在 CPU 上，这部分开销没有被专门优化的内核抵消。而在单并发场景下，K V 本来就不是内存的大头。换到 GPU、长上下文、高并发的场景，结论可能就反过来了。这正是作业四要你回答的问题。

    要点

    优化是否有效，取决于瓶颈在哪里

    小结¶

    • 按最大长度预留 KV 造成浪费
    • PagedAttention：分页按需分配，可共享
    • E4：q8_0 KV 在 CPU 上预填充 89.2 → 36.4 tok/s
    • 优化是否有效，取决于瓶颈

    小结一下。PagedAttention 用分页解决预留浪费，K V 量化在 CPU 上反而变慢。优化有没有效，取决于瓶颈在哪里。练习是手算 K V cache 的大小，和实测的内存差对一对。下一讲，我们讲推测解码。

    课后练习

    按 2×36层×8个KV头×128维×32768×2字节 算 f16 KV（约 4.5GB），q8_0 约减半。预期省约 2.2GB，与 E4 的 RSS 差 2158MB 吻合
