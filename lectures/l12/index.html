    第 12 讲 · 前缀缓存与 request series¶

    追加还是改写？“每一步都写入当前时间”的代价

    视频制作中

    本讲视频将发布在 B 站，届时在这里嵌入播放。下面是讲稿正文。

    第十二讲，前缀缓存与 request series。同样一个 agent，只是换一种写法，成本就可能相差七倍以上。视频里的数据都来自真实运行。

    先看价格：命中与未命中差 50 倍¶

    deepseek-flash 输入价格（高峰价，美元 / 百万 token）

    项目 数值
    命中缓存 $0.006
    未命中 $0.30

    先看价格。DeepSeek flash 的输入分两种：命中缓存的部分，每百万 token 只要零点零零六美元；没有命中的部分是零点三美元，相差整整五十倍。所以输入能不能命中缓存，几乎决定了 agent 的输入成本。

    要点

    输入能否命中缓存，几乎决定了输入成本

    agent 的请求：每一步都是上一步加一点¶

    开头和上一步一字不差，就能命中缓存

    第 1 步    系统提示 + 工具 | 任务
第 2 步    命中：与第 1 步相同 | 新增
第 3 步    命中：与第 2 步相同 | 新增

    再看 agent 的请求是什么样的。每一步，agent 都要把系统提示、工具定义和之前的全部消息重新发一遍，再加上这一步新增的一小段内容。只要开头的部分和上一步一字不差，这部分就能命中缓存，我们只需要为新增的那一小段付全价。

    要点

    只为新增的那一小段付全价

    真实数据：DSH 跑 20 道 SWE-bench（M0 基线）¶

    无缓存≈8.3M 输入×$0.30 + 0.17M 输出×$1.20（每题均值×20 推算）

    项目 数值
    实际花费（高峰价） $0.36
    假如没有缓存（估算） ≈$2.70

    这是课程团队试做阶段的 DSH 基线。二十道 SWE bench 题，每题平均输入约四十一万五千 token，命中率百分之九十五点八，按高峰价一共花了零点三六美元。如果完全没有缓存呢？用每题均值乘以二十，总输入约八百三十万 token，全部按未命中价零点三美元每百万计算，再加上输出，大约两点七美元，是实际花费的七点五倍左右。

    要点

    命中率 95.8%；没有缓存约贵 7.5 倍

    反面教材：在系统提示开头写入当前时间¶

    缓存按前缀匹配，第一个 token 变了，后面全部作废

    第 1 步    时间 10:00:01 | 系统提示 + 工具 + 历史
第 2 步    时间 10:00:09 | 内容相同，但全部未命中

    来看一个反面教材：在系统提示的开头写入当前时间。这看起来人畜无害，但时间每一步都在变，请求的第一个 token 就不一样了。缓存是按前缀匹配的，开头一变，后面的内容再相同也没有用，整个请求都会按未命中计费。

    要点

    开头一变，整个请求按未命中计费

    实验：stable 与 timestamp 各跑五步¶

    同一段对话，真实 DeepSeek API

    $ python cache_demo.py stable timestamp append
=== stable ===
step 1: prompt= 3177  cache_hit=    0  miss= 3177  hit_rate= 0.0%
step 2: prompt= 3208  cache_hit= 3072  miss=  136  hit_rate=95.8%
step 3: prompt= 3252  cache_hit= 3072  miss=  180  hit_rate=94.5%
step 4: prompt= 3271  cache_hit= 3072  miss=  199  hit_rate=93.9%
step 5: prompt= 3293  cache_hit= 3072  miss=  221  hit_rate=93.3%

=== timestamp ===
step 1: prompt= 3197  cache_hit=    0  miss= 3197  hit_rate= 0.0%
step 2: prompt= 3225  cache_hit=    0  miss= 3225  hit_rate= 0.0%
step 3: prompt= 3255  cache_hit=    0  miss= 3255  hit_rate= 0.0%
step 4: prompt= 3276  cache_hit=    0  miss= 3276  hit_rate= 0.0%
step 5: prompt= 3306  cache_hit=    0  miss= 3306  hit_rate= 0.0%

    我们用真实的 API 做个实验。同一段对话，用三种写法各跑五步。第一种，系统提示保持不变，从第二步起命中率就在百分之九十五左右。第二种，把时间写进系统提示，五步全部是零。

    要点

    stable 约 95%；timestamp 五步全是 0

    实验：append，把时间放到最新一条消息里¶

    同一段对话，真实 DeepSeek API

    $ python cache_demo.py stable timestamp append
=== append ===
step 1: prompt= 3196  cache_hit= 2944  miss=  252  hit_rate=92.1%
step 2: prompt= 3251  cache_hit= 3072  miss=  179  hit_rate=94.5%
step 3: prompt= 3314  cache_hit= 3072  miss=  242  hit_rate=92.7%
step 4: prompt= 3354  cache_hit= 3200  miss=  154  hit_rate=95.4%
step 5: prompt= 3406  cache_hit= 3200  miss=  206  hit_rate=94.0%

    第三种，时间信息还在，但放到最新一条消息里，命中率又回到了百分之九十以上。同样的信息，放在开头还是追加在末尾，结果完全不同。

    要点

    同样的信息，追加在末尾，命中率回到 90% 以上

    DSH 的做法：能追加就不改写¶

    when the prepared call declares systemPromptUpdate: 'in-history', a non-empty prompt change inside a continuing request series is appended after the cached history, so the prefix through that history stays reusable.

    —— packages/core/agent-loop/README.md L166 @ dsh-v0.2.2-rc.2

    DSH 把这个原则直接做进了 agent loop。系统提示需要更新时，如果路由支持在历史中更新，并且还在同一个 request series 里，DSH 会把新的提示追加到历史末尾，前缀照常命中。只有两种情况会把提示合并回开头：路由不支持；或者开启了新的 series，而且提示文本确实变了。提示没变时，即使开启新 series，也不会改写。

    要点

    续接 series 内追加；新 series 且文本变化或路由不支持时才合并

    什么会开启新的 request series¶

    packages/core/agent-loop/README.md @ dsh-v0.2.2-rc.2

    • agent/pre-step 的决策声明了 startsRequestSeries
    • 会话内容被替换过，例如压缩或图片卸载
    • 路由不支持工具更新时，工具定义变化会迫使提示合并到开头
    • 恢复会话、切换模型本身不开新 series；但缓存按模型区分，换模型照样未命中

    那么什么情况会开启新的 series？一是插件在每一步开始前的钩子里明确声明要开启；二是会话内容被替换过，比如做了压缩。另外，如果路由不支持工具更新，工具定义一变，提示也要合并回开头。恢复会话或切换模型，本身不会开启新的 series；但要注意，前缀缓存是按服务商和模型分开的，换了模型，前缀照样不会命中。

    要点

    写插件时要清楚：你的改动会不会打断前缀

    小结¶

    • 缓存按前缀匹配
    • 命中与未命中差 50 倍
    • 会变的信息放在末尾
    • 系统提示和工具定义保持稳定，能追加就不改写

    小结一下。缓存按前缀匹配；命中和未命中差五十倍；会变化的信息要放在末尾；系统提示和工具定义要保持稳定。课后小练习：把同一段三千 token 左右的提示连发三次，再把当前时间放到开头连发三次，对比用量里的命中 token 数。预期前者从第二次起几乎全部命中，后者始终是零。下一讲，我们讲插件开发。

    课后练习

    15 分钟：同一约 3k token 提示连发 3 次，再把时间戳放到开头连发 3 次；预期前者第 2、3 次命中约 3k，后者命中为 0
