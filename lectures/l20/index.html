    第 20 讲 · 前缀复用¶

    cache_prompt、RadixAttention，以及 agent 与推理服务的协同设计

    视频制作中

    本讲视频将发布在 B 站，届时在这里嵌入播放。下面是讲稿正文。

    第二十讲，前缀复用。在第十二讲，我们从 API 用户的角度看过前缀缓存。今天站到推理服务这一边，看它是怎么实现的，以及 agent 该怎么配合。

    agent 的请求天然共享前缀¶

    每一步都是在上一步的基础上追加

    第 1 步    系统提示 + 工具 | 任务
第 2 步    系统提示 + 工具 | 任务 | 步骤 1
第 3 步    系统提示 + 工具 | 任务 | 步骤 1 | 步骤 2

    agent 的请求天然共享前缀。每一步都是在上一步的基础上，追加一次工具调用和结果。系统提示、工具定义、之前的历史，全都一模一样，只有最后一小段是新的。如果推理服务能记住前面那部分的 K V cache，就可以只预填充新增的部分。

    要点

    只有最后一段是新的

    llama-server：cache_prompt¶

    单个槽位里保留上一次的 KV cache

    • 新请求进来，先和槽位里已有的 token 比较
    • 相同的前缀直接复用，只计算不同的部分
    • timings 里的 cache_n 告诉你复用了多少 token
    • 前缀一旦有一个 token 不同，后面全部失效

    在 llama server 里，这个功能叫 cache prompt。新请求进来时，先和槽位里已有的 token 逐个比较，相同的前缀直接复用，只计算后面不同的部分。返回的耗时统计里，cache n 就是复用的 token 数。要注意，只要前缀里有一个 token 不同，后面的缓存就全部失效。

    要点

    命中靠的是逐 token 完全一致

    E2 实测：开关 cache_prompt¶

    a4_E2：Qwen3-8B Q4，Xeon Gold 6354，-t 16

    $ python assignment4/engine/bench.py --exp E2 --model models/Qwen3-8B-Q4_K_M.gguf --server llama.cpp/build/bin/llama-server
  "cache_off": {
   "first_prompt_ms": 51540,
   "first_prompt_n": 4632,
   "second_prompt_ms": 52378,
   "second_prompt_n": 4632,
   "second_cache_n": 0
  },
  "cache_on": {
   "first_prompt_ms": 582,
   "first_prompt_n": 15,
   "second_prompt_ms": 625,
   "second_prompt_n": 15,
   "second_cache_n": 4617

    看实验二的真实结果。关闭缓存时，第二次请求要重新预填充四千六百多个 token，用了五十二秒多。打开缓存后，四千六百一十七个 token 直接复用，只需计算十五个。预填充时间从五十多秒降到不到一秒，快了八十多倍。

    要点

    第二次请求预填充：52378 ms → 625 ms

    RadixAttention：多请求共享前缀树¶

    SGLang 论文的思路（只讲不做）

    • 把所有缓存过的 token 序列组织成一棵基数树
    • 不同请求只要前缀相同，就共享同一段 KV cache
    • 按 LRU 淘汰不常用的分支
    • 适合多个 agent 共用系统提示、并行采样等场景

    llama server 的复用只在单个槽位里。SGLang 论文提出的 RadixAttention 更进一步：把所有缓存过的 token 序列组织成一棵基数树，不同请求只要前缀相同，就能共享同一段 K V cache，内存不够时按最近最少使用的规则淘汰分支。

    要点

    从单槽位复用，到全局前缀共享

    协同设计：agent 要配合缓存¶

    作业四 L3 的要求

    • 保持系统提示和工具定义稳定，不要每步写入当前时间
    • 只追加，不改写历史消息
    • 压缩上下文会打断前缀，要权衡时机
    • 证明预填充时间下降，且解决率不变差

    所以 agent 必须配合缓存。保持系统提示和工具定义稳定，不要在每一步写入当前时间。只追加，不改写历史消息。压缩上下文会打断前缀，要权衡时机。作业四第三关要求你证明，修改后的 agent 预填充时间下降了，而且解决率没有变差。

    要点

    缓存命中率，是 agent 写出来的

    回顾：云端也一样¶

    第 12 讲与 M0 数据

    • DSH 基线在 20 题上的缓存命中率 95.8%
    • 云端按命中和未命中分别计价
    • 本地：省的是时间；云端：省的是钱

    云端也是同一个原理。试做阶段的实测里，DSH 基线在二十道题上的缓存命中率是百分之九十五点八。在本地，前缀复用省的是时间；在云端，省的是钱。

    要点

    同一个原理，两种收益

    小结¶

    • agent 请求天然共享前缀
    • cache_prompt：逐 token 匹配，复用 KV cache
    • E2：第二次预填充 52378 → 625 ms
    • RadixAttention：多请求共享前缀树
    • agent 要只追加、保持前缀稳定

    小结一下。前缀复用让第二次请求的预填充快了八十多倍，但命中率取决于 agent 怎么写。练习是在第二个请求开头插一个空格，看缓存命中是不是归零。下一讲，我们讲显存与内存管理。

    课后练习

    在 E2 第二个请求的开头插入一个空格再跑一次（约 2 分钟）。预期：second_cache_n 从 4617 掉到接近 0，预填充回到约 50 秒；解释为什么
