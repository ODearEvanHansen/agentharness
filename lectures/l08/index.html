    第 8 讲 · 评测基础设施¶

    容器隔离、出网白名单、镜像分发与可复现性

    视频制作中

    本讲视频将发布在 B 站，届时在这里嵌入播放。下面是讲稿正文。

    第八讲，我们讲评测基础设施。agent 要在真实代码仓库里执行命令，评测又要能被别人复现，这两件事都要靠基础设施来保证。

    课程评测架构¶

    任务容器默认断网，只能经白名单代理访问 DeepSeek API

    任务容器     SWE-bench 官方镜像 | 限 4 核 · 8GB
网络       --internal 网络 | egress 代理 tinyproxy
出网       api.deepseek.com ✓ | 其他地址 ✗
评测       官方 swebench 5.0.2 | 判分

    先看整体架构。每道题跑在 SWE bench 官方预构建的镜像里，容器限制四核 CPU 和八个 G 的内存。容器接入一个内部网络，默认断网，只能经过一个白名单代理访问 DeepSeek 的 API。最后，用官方的 swebench 评测工具判分。

    要点

    隔离由容器负责，出网由白名单负责

    出网白名单：四条命令¶

    摘自 infra/README.md

    docker build -t agentharness-egress:0.1 infra/egress
docker network create --internal agentharness-net
docker run -d --name agentharness-egress agentharness-egress:0.1
docker network connect agentharness-net agentharness-egress
# assignment container:
docker run --network agentharness-net -e HTTPS_PROXY=http://agentharness-egress:8888 ...

    白名单的搭法很简单。先构建代理镜像，再建一个 internal 网络，把代理接进去。作业容器只接这个网络，并把代理环境变量指向代理。怎么验证呢？在容器里访问 DeepSeek，应该返回状态码四零一，说明连通了，只是没带 key；访问 GitHub 应该失败。

    要点

    验证：DeepSeek 返回 401，github.com 连不上

    镜像分发：为什么用 GHCR¶

    SWE-bench 镜像又大又多

    • 每道题一个镜像，约 3GB；20 题合计约 60GB，M0 拉取用了约 15 分钟
    • 课程把镜像同步到 ghcr.io，一个 package，每个实例一个 tag
    • 同步由 GitHub Actions 用 crane 直接复制，不在本地中转
    • 国内访问 GHCR 不稳定，必要时用代理或镜像加速（待实测）

    接下来是镜像分发。SWE bench 每道题一个镜像，每个大约三个 G，二十道题加起来大约六十个 G，试做阶段拉取用了大约十五分钟。课程把这些镜像同步到了 GHCR，每个实例一个 tag，由 GitHub Actions 直接复制，不经过本地。国内访问 GHCR 还不稳定，镜像加速方案还在实测。

    要点

    评测环境本身就是课程的一部分

    踩坑记录¶

    都写进了课程文档

    • swebench 5.x 必须用数据集名 SWE-bench/SWE-bench_Verified，旧名会报 KeyError
    • SWE 模式下 patch 目录只读挂载进任务容器，插件路径必须是绝对路径
    • DSH 运行时是自包含二进制，只读挂进容器即可运行，不需要 Node
    • 评测脚本必须设每题超时：20 题、3 路并发约需 40 分钟

    再说几个踩过的坑。swebench 五点几版本必须使用新的数据集名，用旧名会直接报错。插件和 patch 的路径必须写绝对路径。DSH 的运行时是一个自包含的二进制，只读挂进容器就能跑。另外，耗时长尾很明显，评测脚本要给每题设超时，二十道题三路并发大约要四十分钟。

    要点

    小坑不写下来，每个学员都要重踩一遍

    每一行：耗时、请求数、工具调用数、成本、补丁行数

    可复现性：把能固定的都固定¶

    • 抽样固定随机种子 2680，题号写进 instances.txt
    • 锁定版本：DSH 0.2.2rc2（PyPI 实际可装），作业和源码引用都对齐它
    • 换镜像源要重验：用 GHCR 重新评测，loop 18/20、DSH 17/20，与 Docker Hub 一致
    • 模型输出本身有随机性：结论要靠重复运行和对照，第十五讲细讲

    最后是可复现性。能固定的都要固定：抽样用固定的随机种子，版本锁定到课程锁定版本，也就是零点二点二的第二个候选版。换了镜像来源，也要重新验证，课程用 GHCR 重新评测，loop 十八道、DSH 十七道，和原来完全一致。但要注意，环境可复现不等于结果可复现，模型输出本身就有随机性，这一点第十五讲再细讲。

    要点

    环境可复现 ≠ 结果可复现

    白名单防不住什么¶

    出网白名单是一道防线，不是全部

    • 只有容器接 --internal 网络时才生效；直接用默认网络等于没设
    • 防不住经 api.deepseek.com 本身外泄：key 和数据都能随请求发出
    • 用一把课程专用 key，并在平台上设消费上限
    • 用完或怀疑泄露就立刻作废这把 key

    还要讲清楚白名单防不住什么。第一，它只有在容器接入内部网络时才生效，如果容器用的是默认网络，代理形同虚设。第二，它防不住通过 DeepSeek 的 API 本身外泄：被提示注入的 agent，完全可以把 key 或代码塞进一次正常的 API 请求里发出去。所以建议你为这门课单独创建一把 API key，在平台上设好消费上限，用完或者怀疑泄露就立刻作废。

    要点

    专用 key + 消费上限，把最坏情况限定住

    小结¶

    • 任务跑在容器里，网络默认断开
    • 出网只放行 api.deepseek.com
    • 镜像经 GHCR 分发，约 3GB/题
    • 固定种子、锁定版本、换源重验
    • 专用 key + 消费上限

    小结一下。任务在容器里跑，网络默认断开，只放行 DeepSeek；镜像通过 GHCR 分发；能固定的种子和版本都要固定。白名单防不住经 DeepSeek API 本身的外泄，所以要用专用、限额的 key。课后花十五分钟搭好白名单，预期访问 DeepSeek 返回状态码四零一，访问 GitHub 失败。下一讲，我们讲工具设计。
